# RepoRove 产品需求与开发交接说明

版本：0.1 · 整理日期：2026-10-06 · 目标平台：Android

本文与同目录的 `原型.html`、`prototype/` 源码、`screenshots/` 截图一起构成开发基线。接手者先读第 1–4 节，再体验第 11 节的路径，即可开始项目骨架、导航、主题与数据接入验证。

**产品定位：一个能像刷社交媒体一样浏览 GitHub、查看仓库状态，并让用户决定界面内容和布局的 Android 客户端。**

## 1. 已确认的产品方向

以下来自用户明确表达或本轮讨论中接受的方向。原型中的具体数量、示例文案与按钮位置，除明确列入这里的内容外，属于实现参考。

| 编号 | 已确认事项                                        | 开发含义                                                                                  |
| ---- | ------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| D01  | 英文名为 **RepoRove**                             | 界面、项目说明和后续工程统一使用此拼写；中文名暂缓，不继续定名                            |
| D02  | 目标为 GitHub 的 Android 客户端                   | 浏览器原型用于验证产品；正式交付目标是手机 App                                            |
| D03  | 使用体验应舒适、便捷，像刷社交媒体一样浏览 GitHub | 支持持续浏览、快速进入内容、返回原位置、收藏与查看项目变化                                |
| D04  | 用户不满意现有产品尤其官方 App 的审美和杂乱感     | 功能可以完整，但界面入口和内容由用户选择，避免所有功能挤在首屏                            |
| D05  | 默认采用「纸感阅读」方向                          | 温暖的浅色底、清晰文字、克制的分隔线与图标；现阶段先把这个方向做好                        |
| D06  | 最不喜欢此前「柔和卡片」方案的配色和风格          | 默认视觉避免大量柔彩、圆润大卡片和装饰性层级；这不等于禁止所有卡片或色彩                  |
| D07  | 后续支持多种主题风格                              | 主题与功能布局解耦；当前只确定纸感阅读，其余主题方案尚未定稿                              |
| D08  | 支持自定义界面布局和选项卡                        | 用户可以勾选显示哪些功能，并决定排列顺序；例如只保留 Explore、Inbox，隐藏不需要的 Copilot |
| D09  | 仓库信息和状态希望覆盖全面，也能自定义展示        | 必须有清楚的仓库内容入口；概览优先级和可见模块可以调整                                    |
| D10  | 搜索支持选择内容类型                              | 用户能先选仓库、代码、Issue、PR、用户等类型，再使用该类型适用的条件                       |
| D11  | 页面主体应绝大部分是有用内容，阅读效率优先        | 缩小标题与页头，去掉大标语和装饰文字，让项目列表进入首屏                                  |
| D12  | 保留 GitHub Explore 本身有用的功能组织思路        | 不因重做视觉而删掉有价值的发现、筛选和项目浏览能力；真实数据来源需技术验证                |
| D13  | AI 翻译与镜像仓库配置是后续期望                   | 记录为扩展方向，当前原型不假装已实现，也不把它们设为首版必备                              |

### 1.1 用户原意摘录

- 「方便我在手机上像用社交媒体一样刷 GitHub 和看仓库状态」。
- 「用户可以自己决定要展示什么功能」。
- 「看仓库状态应该说都要展示（也可以支持自定义）」。
- 「搜索的话也是支持可以选择按什么类型搜索」。
- 「界面的主体绝大部分占比应该都是有用的内容」。
- 「后面做得好支持 AI 翻译和镜像仓库配置更好」。

这些描述应优先于原型里临时采用的营销文案、布局预设和模拟行为。用户说「其他还行我再看看」，表示当前原型可继续作为讨论基础，不能理解为逐项确认了所有页面细节。

### 1.2 名称与品牌边界

正式英文名是 RepoRove。旧临时名「栖页」不再作为产品名。中文名暂停选择；未敲定正式 Logo、吉祥物、域名、包名或发布主体。原型里的线条图标只是占位图标。用户自行检索未发现同名项目；本次没有另做名称占用核查。

## 2. 原型基线与当前状态

### 2.1 应以哪份原型为准

以本文件夹的 `原型.html` 和 `prototype/` 为准，发现页采用已经缩减的版本：

- 没有「好项目，值得慢慢发现」的大标题、开源漫游编号、星号装饰和页尾抒情文案。
- 顶部保留小型「发现」页头、搜索入口、头像和实用的分类筛选。
- 所有项目使用相近的列表层级，首个项目不再额外做大封面。
- 保留项目名、作者、简介、主题、语言、Star、更新时间与收藏操作。

**原型体现的是信息组织、视觉方向和交互目标，不是已接通 GitHub 的客户端。**

### 2.2 已有展示与操作

| 部分       | 原型已有内容                                                    | 操作性质                                                   |
| ---------- | --------------------------------------------------------------- | ---------------------------------------------------------- |
| 发现       | 项目列表、主题过滤、专题入口                                    | 过滤少量虚构项目；「为你」为演示命名，不代表已接入推荐系统 |
| 动态       | Release、PR、讨论、提交的事件样例                               | 按本机模拟订阅过滤固定事件；不是 GitHub 实时数据           |
| 收件箱     | 全部、未读、已完成，通知进入详情                                | 已读、完成和撤销只修改本机状态                             |
| 资料库     | 参与仓库、Star、稍后看、订阅、下载                              | 内容依据本机示例状态更新                                   |
| 搜索       | 仓库、代码、Issue、PR、用户                                     | 关键词与类型过滤示例数据；语言、排序、状态筛选可体验       |
| 仓库概览   | 状态、README、版本、活动、待办、CI                              | 依据模块设置显示和排序                                     |
| 代码       | 分支、目录、文件、行号、换行、复制                              | 少量共享示例文件，不是完整 Git 文件系统                    |
| Issue      | 开放/关闭、标题筛选、详情、评论、草稿                           | 评论和草稿保存在本机，未提交至 GitHub                      |
| PR         | 对话、变更、提交、检查与审核入口                                | 部分 diff、样例提交和本机审核结论                          |
| 发布       | 版本说明、文件、历史版本入口                                    | 只有模拟下载记录，没有真实安装包                           |
| Actions    | 工作流、成功/失败运行、步骤和日志                               | 重跑只演示排队状态，不执行真实构建                         |
| 更多       | Discussions、Projects、统计、安全、贡献者、文档、Packages、部署 | 部分使用弹窗或示例摘要，不是完整功能页面                   |
| 个人与工作 | 资料、组织、贡献图、待审核、参与事项                            | 演示账号与数据                                             |
| 设置       | 选项卡选择/排序、启动页、模块选择/排序、密度、字号、布局预设    | 即时保存到本机浏览器                                       |

### 2.3 不应照搬的演示细节

- 模拟状态栏的时间、信号、电池、手机外框与桌面页面索引，是展示工具。正式 Android 应使用系统状态栏、安全区域和正常导航返回栈。
- 示例账号、仓库、日期、统计、文件大小、贡献图和文案均为占位内容。统计数量不保证与几条示例记录对应。
- 不同示例仓库部分共用 Issue、PR、代码与 CI 数据；真实实现必须按仓库隔离。
- 示例「订阅」同时影响动态列表，不代表真实 GitHub Watch 与用户动态流具有同样关系。
- 原型「最近更新」没有接入真实服务端排序；正式实现必须请求或排序真实更新时间。
- 原型正文是示例内容，没有完整 Markdown、图片、附件和代码高亮能力。
- 原型中的字号百分比、1–5 个选项卡、两种预设，是当前交互基线和开发建议，不是用户逐项指定的产品限制。
- 浏览器里所有按钮的即时成功与撤销，不代表远端接口一定可逆、立即成功或支持同样操作。

## 3. 目标用户、任务与范围

### 3.1 首要任务

1. 打开手机快速发现值得关注的项目，扫过简介与状态，进入 README 或仓库内容。
2. 跟踪已关注项目的发布、提交、Issue、PR 和构建结果。
3. 查收与自己有关的通知，进入上下文，知道接下来需要做什么。
4. 分类搜索 GitHub，避免所有对象混在一个结果列表里。
5. 组织收藏、稍后看与常用仓库，按个人习惯摆放界面。

产品应同时照顾以浏览为主的用户和需要跟踪/维护项目的用户。个人布局可突出不同内容；不要把每位用户都当成每天必须处理 CI 或 PR 的维护者。

### 3.2 分期建议

以下是便于启动开发的建议排序，**不是用户已经确认的发布时间表**。

| 阶段              | 建议范围                                                                                           | 交付条件                                                 |
| ----------------- | -------------------------------------------------------------------------------------------------- | -------------------------------------------------------- |
| A：基础验证       | Android 工程、纸感样式、自定义导航与模块、缓存模型、GitHub 认证和通知接口验证                      | 能用模拟数据跑通原型主路径；真实凭据完成接口可行性验证   |
| B：首个可用版本   | 公开仓库浏览、类型搜索、README/代码、真实 Star、稍后看、基本发布信息、仓库状态、可用的登录与收件箱 | 所有展示数据来源明确；成功、空、错误、分页和离线状态可用 |
| C：协作与跟踪完善 | 真实动态、通知处理、评论与 Issue、PR 审核、完整 diff、Actions、下载管理、用户/组织详情             | 远端写操作、权限与失败恢复正确；账号状态能同步           |
| D：进阶扩展       | 更多主题、AI 翻译、镜像配置、更完整的 Projects/Discussions/统计/Packages/部署                      | 各扩展有独立设置、数据来源和明确能力边界                 |

不能为了分期直接删掉用户关心的仓库信息。暂未原生实现的低频功能，可以保留清晰入口并打开 GitHub 网页；入口必须说明实际行为。

## 4. 界面原则与布局规则

### 4.1 内容占比

- 页头是工具栏，不做海报。列表页标题建议约 18–22sp；不要用大型标题占据多行。
- 首屏优先用于项目、通知和状态。避免大段欢迎词、情绪文案、编号装饰、重复提示与大幅留白。
- 发现页的改版在 390×844 CSS 像素、默认字号与当前示例数据下，首屏可完整展示 3 个项目，主内容滚动区域约 81% 可用于项目列表。这是对照样本，不是对所有屏幕和系统字号强行要求 3 项。
- 压缩页头、无效模块与间距，保持正文、元信息和点击区域清楚可读；不要靠把所有文字缩成小字提高密度。
- 标题、简介与状态信息优先；语言、更新时间、标签用于快速扫描；次要操作收进菜单或详情。

### 4.2 纸感主题

| 元素       | 当前基线                     | 正式实现要求                                         |
| ---------- | ---------------------------- | ---------------------------------------------------- |
| 页面底色   | `#FAF8F2`                    | 可通过主题 token 管理，减少视觉噪声                  |
| 主要文字   | `#30372D`                    | 保持对比度，不把主要正文做成浅灰装饰                 |
| 正文辅助色 | `#67715C`                    | 统一阅读层级，实际对比度按界面验证                   |
| 强调色     | `#596746`                    | 用于选中状态与重要操作，面积克制                     |
| 分隔线     | `#E3E2D8`                    | 列表主要靠细线和间距分组                             |
| 字体       | 系统无衬线正文，少量衬线标题 | 中文显示稳定，支持系统字体缩放；避免依赖远程字体服务 |
| 容器       | 小圆角、低阴影、清楚边界     | 状态摘要可分组；默认不堆叠大块柔彩卡片               |

以上色值和尺寸是原型参考；最终要在真实 Android 设备上校验。主题 token 至少覆盖背景、文字、辅助文字、强调、边界、状态色、字体与形状。换主题不改变选项卡和内容设置。

### 4.3 导航自定义

候选主入口：`discover` 发现、`feed` 动态、`inbox` 收件箱、`library` 资料库、`work` 我的工作、`profile` 我的、`search` 搜索。

原型默认顺序：**发现 → 动态 → 收件箱 → 资料库**。

建议基线规则：

1. 用户可以选择显示项，并调整顺序；原型用上下箭头，正式版可增加拖动排序。
2. 手机底部导航保留 1–5 项；超出时先提示用户调整，不自动插入第 6 项。
3. 至少保留一个主入口，避免应用启动后无法导航。
4. 启动页必须属于已显示项；隐藏当前启动页时，回退到新顺序第一项并立即保存。
5. 隐藏只是隐藏快捷入口，不删除功能或内容。搜索、个人主页、设置等必要能力仍应有可发现的入口；仅保留收件箱等特殊布局时，也必须能访问设置。
6. 仓库和内容详情使用真实返回栈；从收件箱进入 PR，返回应回到原收件箱位置。
7. 按稳定 ID 保存配置，不按中文显示名或列表下标保存。
8. 恢复默认布局只恢复布局与阅读配置，不清空 Star、稍后看或账号数据。

Copilot 是用户举例说明“可隐藏不常用功能”的对象，没有确认必须加入首版，也没有要求为它保留默认入口。

### 4.4 仓库概览自定义

可选模块：`status` 状态摘要、`readme` README、`release` 最新版本、`activity` 最近活动、`tasks` 我的待办、`ci` 构建与部署。

原型默认顺序：**状态摘要 → README → 最新版本 → 最近活动**。

模块显示与顺序即时保存。隐藏概览模块不隐藏对应的仓库栏目。允许隐藏全部概览模块，显示简短的配置入口；不要自动恢复用户隐藏的内容。

当前采用全局仓库概览模板。逐仓库覆写模板与任意尺寸的自由拖拽组件，尚未确认，不应默认为首版要求。

### 4.5 阅读设置

原型提供舒展/紧凑密度和 90%、100%、110%、120% 正文字号；正式实现需与系统字体缩放共同工作。设置应即时预览，并应用于 README、简介、发布说明和评论。代码内容可使用独立字体与横向滚动，避免改字号导致主要工具不可访问。

## 5. 全局页面需求

### 5.1 发现 / Explore

**目的：快速找到项目，而非阅读产品宣传。**

项目条目应提供作者/组织、项目名、简介、主要语言、Star、更新时间，以及根据数据情况展示的主题、可见性、Fork、归档状态。Star 和稍后看是不同操作，不能混成同一种收藏。

需要有主题或类别筛选、可用的排序与进入详情操作。主题聚合、趋势、近期更新和兴趣推荐是候选组织方式；最终标签与真实来源尚未敲定。原型的「为你 / 最近更新 / 专题」可以作为布局参考，不应视为最终承诺的推荐算法。

实现判断：官方搜索与 Events 文档本身不能证明第三方客户端能直接复刻 GitHub 网页的 Explore 推荐或 Trending。开发时先验证数据来源。若实际采用仓库搜索或发布时间排序，应使用准确名称，例如“最近更新”“近期活跃”，避免冒称官方推荐。相关查询能力见 [GitHub Search API](https://docs.github.com/en/rest/search/search)。

长列表采用分页与加载更多；刷新后保留可恢复的阅读位置。过滤结果为空时提供清除条件操作。

### 5.2 动态

条目按时间展示项目及人员的事件，包含来源、事件类型、项目、主要变化、作者、时间和进入对应内容的入口。优先关注 Release、PR、Issue/讨论、提交与构建结果，提供事件类型过滤。

数据来源须分别标记：GitHub 用户/仓库活动、本地关注仓库聚合、版本检查。Star、Watch、关注用户和本地订阅不是同一概念；过滤与聚合规则必须显式实现。

GitHub Events 有事件数量/时间范围及延迟限制，不能宣称这是完整实时动态历史。展示更新状态与最后获取时间，按需拉取与缓存，不能逐仓库无限高频轮询。见 [Events API](https://docs.github.com/en/rest/activity/events)。

### 5.3 收件箱 / Inbox

核心字段：通知源、线程 ID、仓库、对象类型、标题、触发原因、更新时间、未读状态、目标链接。重点区分审核请求、提及、分配事项、参与讨论和 CI 等理由。

核心行为：全部/未读/已完成视图，进入上下文，标为已读，完成/归档，批量处理与明确反馈。登录不足、权限不足、过期凭据和空列表分别处理。

**原型“撤销”不能直接照搬到真实 API：**

- 本机演示允许任意恢复；远端标已读和完成操作需要验证有无相应逆操作。
- 对需要撤销窗口的完成操作，可先做本地暂存，窗口结束再提交；提交后不承诺远端可撤销。
- 没有对应的“恢复未读”接口时，不提供假同步的撤销。若只有本机显示恢复，应明确其范围。
- 已完成列表可能需要本地归档记录支持；不要假设服务端提供完整跨端归档历史。
- 版本更新或自定义订阅提醒如果由客户端生成，应标记为本地通知，不能伪造 GitHub 的 reason。

当前 GitHub 通知文档对 token 类型有限制，属于认证选型的首个验证项，详见第 9.2 节。[通知 API](https://docs.github.com/en/rest/activity/notifications)

### 5.4 资料库

分开管理参与/拥有仓库、GitHub Star、稍后看、本地或 GitHub 订阅，以及版本下载。支持当前分组内搜索与合理排序。

Star 与 GitHub 同步；稍后看属于客户端个人数据，不依靠给仓库加 Star 代替。客户端自建分组、置顶、跨设备同步与批量管理属于后续可评估范围，当前原型未完成这些能力。

下载应展示进度、结果、保存位置与可移除记录。模拟 APK 文件不能作为真实下载入口发布。

### 5.5 搜索

| 类型      | 必要结果内容                                                    | 适用筛选建议                                   |
| --------- | --------------------------------------------------------------- | ---------------------------------------------- |
| 仓库      | 作者、名称、简介、语言、Star、更新时间                          | 语言、主题、更新时间、Star、Fork、可见性与范围 |
| 代码      | 仓库、文件路径、语言、匹配片段                                  | 仓库、路径、语言；只提供接口实际支持的排序     |
| Issue     | 仓库、编号、标题、状态、标签、作者、评论                        | 开放/关闭、标签、作者、分配者、参与者、仓库    |
| PR        | 仓库、编号、标题、Open/Draft/Merged/Closed、作者、审核/检查状态 | 状态、作者、审核请求、仓库                     |
| 用户/组织 | 头像、名称、登录名、简介和相关统计                              | 用户/组织区分、范围；按接口支持能力提供条件    |

搜索类型明确可选；切换类型后移除或忽略不适用条件。条件不能只改变按钮选中状态而不影响查询。结果允许部分信息延迟补全，避免为列表每行请求全部仓库数据。

正式查询使用服务端搜索，支持分页、取消旧请求、输入防抖和结果为空提示。Issue 与 PR 可以共享底层查询通道，但必须区分对象类型；PR 的关闭与合并状态不能合并为一个含糊状态。代码搜索能力、认证要求和排序与网页可能不同，按当前 [Search API](https://docs.github.com/en/rest/search/search) 校验，不能复制原型的本地字符串过滤作为正式能力。

### 5.6 我的工作

聚合待审核 PR、自己创建的 PR、被分配/参与的 Issue，以及可操作的检查或部署请求。列表突出“与我有什么关系、现在是什么状态、下一步去哪”。默认是否作为底部入口取决于用户选择。

### 5.7 个人与组织

个人：头像、名称、登录名、简介、位置/公开链接、仓库、Star、关注者/正在关注、贡献活动、组织、账号与设置入口。头像和统计不能为每个页面各自维护互相矛盾的状态。

组织：公开介绍、仓库、成员及权限允许的内容。Teams、组织权限与企业功能可在后续阶段增强；无权限时给明确状态或网页入口。

### 5.8 设置

包含界面与内容、阅读方式、主题、账号与权限、缓存/下载、关于等分区。当前用户最关心的配置是入口勾选、排序与模块展示，应容易发现，避免埋在多层“高级设置”。

## 7. 通用交互、状态与可用性

### 7.1 列表与导航

- 列表项的主要内容可点击，Star、稍后看等次要操作独立；点击收藏不能误进详情。
- 返回恢复筛选、搜索类型和原阅读位置；跳入多层详情后仍能回到进入来源。
- 列表支持首次加载、刷新、分页、无更多数据、空、错误、离线缓存状态。
- 刷新时保留已有内容，避免整个屏幕闪白；加载失败提供重试，不永久空白。
- 新数据不能无提示地让正在阅读的列表大幅跳位。

### 7.2 远端写操作

Star、Watch、评论、Issue、审核、通知处理等远端动作需要真实反馈。可以乐观更新，但失败必须回滚或标为待同步；提交期间避免重复提交。草稿与提交完成是不同状态。

服务端不支持的编辑、撤销或恢复动作，应隐藏、说明或走网页，不用永远成功的 Toast 代替实现。合并、删除、修改仓库管理配置和触发 CI 等高影响行为，采用单独确认与权限检查。

### 7.3 Markdown 与代码

正确处理中文、长英文路径、链接、图片、表格、折叠内容和大文件。渲染不执行仓库提供的脚本；打开外部链接、仓库内部相对路径和附件分别处理。图片懒加载，避免加载后阅读位置跳回顶部。代码行支持横向滚动与可选换行，复制真实内容。

### 7.4 性能与无障碍

按页面和可见模块按需请求；隐藏的模块不因为“可能以后展开”立即请求所有数据。缓存、分页、图片加载和列表虚拟化避免每行重复联网。

交互区域建议至少 48dp，图标有可读标签，状态不只依赖颜色。支持系统字号放大、减少动态效果、深层返回与常见 Android 导航模式。紧凑模式主要减少留白，不能把触控目标缩到难点。

## 8. 数据、配置与本机状态设计

以下是建议的领域模型，正式类型按所选 Android 技术栈落地。字段来源和读/写权限应与 API 响应适配层分离。

| 实体                | 核心标识/字段                                                                             |
| ------------------- | ----------------------------------------------------------------------------------------- |
| Account             | host、user ID、login、头像、授权能力；凭据另存，不混入普通配置                            |
| Repository          | host + 稳定 repo ID，owner/name、说明、属性、统计、默认分支、更新时间、当前账号关系与权限 |
| RepositoryStatus    | 最新版本、主分支检查、Issue/PR 汇总、最近提交、部署；各字段各自有加载/错误状态            |
| TimelineEvent       | 来源、稳定事件 ID、仓库、类型、作者、时间、目标、摘要、缓存获取时间                       |
| Notification        | 来源、thread ID、reason、对象、仓库、未读/本机归档状态、更新时间、目标 URL                |
| SearchQuery         | 类型、关键词、过滤条件、排序、分页游标/页码                                               |
| Issue / PullRequest | 仓库身份 + 编号、远端 ID、作者、正文、状态、标签、评论；PR 另有分支、审核、diff 与 checks |
| Release / Asset     | 仓库、版本 ID/tag、状态、说明、文件 ID、名称、大小、下载源、校验信息                      |
| WorkflowRun         | 仓库、run ID、工作流、触发、分支、SHA、状态、结论、耗时、Jobs/Steps                       |
| LocalCollection     | 用户/本机身份、repo ID、稍后看、置顶/分组等状态                                           |
| DownloadRecord      | 资源、状态、进度、路径、错误、来源，避免凭据写进公开日志或永久 URL                        |
| UserPreferences     | 配置版本、选项卡 ID 和顺序、启动页、概览模块、密度、字号、主题                            |

当前配置基线可表达为：

```json
{
  "schemaVersion": 1,
  "visibleTabs": ["discover", "feed", "inbox", "library"],
  "startTab": "discover",
  "repositoryModules": ["status", "readme", "release", "activity"],
  "density": "comfortable",
  "textScale": 1.0,
  "themeId": "paper"
}
```

配置新增功能时不强制把新功能插进老用户的导航；使用稳定 ID 与版本迁移。非法或失效的配置回退到可用状态，并保留仍有效的选择。账号数据和私有缓存按账号与 host 隔离，退出时明确清除或隔离，避免切换账号时显示另一个账号的数据。

本机稍后看与界面偏好可优先落地。跨设备同步、多个 GitHub 账号与 Enterprise 实例均未确认，不应阻塞第一阶段。

## 9. 技术实施建议与 GitHub 接入要点

### 9.1 Android 工程

建议采用 Kotlin + Jetpack Compose，以可复用组件和主题 token 实现原型。UI/状态管理与数据层分离；按需设置领域层。可参考 Android 的 [应用架构指南](https://developer.android.com/topic/architecture)。这属于技术建议，用户没有指定语言、框架、最低 Android 版本或分发渠道。

建议模块边界：`core-ui`、`core-model`、`core-network`、`core-storage`、`feature-discover`、`feature-inbox`、`feature-repository`、`feature-search`、`feature-settings`。小团队起步可先用 package 分层，避免过度拆成大量构建模块。

数据层提供 mock 与 GitHub 两种实现，让同一 UI 既可演示也可连接真实服务。持久化配置与内容缓存分开。每个页面持有明确 UI 状态，写操作使用独立的提交状态。

当前 React/Vite 源码是产品参考和可运行演示，不代表已经选择用 WebView 包装成 Android App。

### 9.2 先验证认证与通知兼容性

收件箱是用户明确重视的能力。**不能先选好某种 token，再到末期才发现通知接口不兼容。**

截至本次核对，GitHub 通知文档概述强调 classic PAT 认证及 `notifications`/`repo` scope，并明确若干通知接口不支持 GitHub App user/installation token 和 fine-grained PAT。因此，以这些文档为依据，GitHub App 或 fine-grained PAT 不能直接当成已证明可用的收件箱方案。[通知 API 的认证说明](https://docs.github.com/en/rest/activity/notifications)

开发第一步应在受控测试账号中验证：获取用户身份、列出通知、读取目标、标已读、标完成、权限不足与过期处理。classic PAT 可用于开发验证；正式用户登录体验及是否允许 PAT 手动导入尚未确认。

OAuth device flow 无需在客户端嵌入 client secret，可作为移动客户端登录候选；它要求应用注册中启用该流程，并正确处理等待、取消、过期和轮询间隔。OAuth token 能否覆盖本产品全部通知操作，应实际验证，不因授权成功而推定可用。若采用浏览器授权代码流程，按文档校验 PKCE、state 与 token 交换的要求。[OAuth 授权文档](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps)

客户端不存用户 GitHub 密码，不把 client secret 打入 APK。凭据使用系统安全能力保护，日志脱敏。授权尽量按需申请；需要访问私有仓库或写操作时，让用户明白额外权限的用途。

### 9.3 服务接口映射与验证清单

下表是功能接入方向，开发者仍需按所选认证方式逐个确认当前端点、参数和权限。

| 功能             | 接入方向                                                   | 关键验证                                               |
| ---------------- | ---------------------------------------------------------- | ------------------------------------------------------ |
| 身份、资料、组织 | 当前用户、用户与组织相关 API                               | 登录返回的 user ID 与本机账号匹配                      |
| Explore/搜索     | 官方仓库、代码、Issue/PR、用户/Topics 搜索                 | 分类、范围、分页、排序、代码搜索能力、结果是否完整     |
| 动态             | 用户收到的事件、仓库事件、按需获取版本变化                 | 来源、延迟、范围、Watch/Star/关注的区别                |
| Inbox            | Notifications/Threads                                      | token 兼容、轮询、已读与完成、归档历史/撤销限制        |
| 仓库概览         | repo 元信息、README、语言、版本、Issue/PR、checks          | 全部字段不能因一组请求失败而丢失；分页列表长度不是总数 |
| 代码             | Contents/Trees、Branches/Tags、Commits、比较               | 分支 ref、二进制/大文件、目录截断、相对链接            |
| Issue/评论       | Issues、Issue comments、标签/里程碑、反应                  | REST Issue 对象中识别 PR；读取与写入权限分开           |
| PR               | Pull requests、files、commits、reviews、checks/statuses    | Draft/Open/Closed/Merged 的正确分类、diff 完整性       |
| Releases/下载    | Releases、Assets                                           | 草稿/预发布权限、正确文件、重定向、下载认证            |
| Actions          | Workflows/Runs/Jobs、日志与 Artifacts                      | 工作流结果、日志下载、权限、过期产物、真实重跑         |
| 更多             | Discussions/Projects 可考虑 GraphQL，其余对应 REST/GraphQL | 先验证，再决定原生页面或网页回退                       |

### 9.4 请求、缓存与错误

客户端遵循服务端分页与缓存信息，统一调度请求。对可缓存资源使用 ETag/Last-Modified 条件请求；对限流按 `Retry-After`、`X-RateLimit-Reset` 等响应处理。通知/活动轮询尊重 `X-Poll-Interval`，不使用固定秒级后台轮询。[GitHub REST API 最佳实践](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api)

建议分别处理：离线/超时、认证失效、权限不足、内容不存在或不可访问、限流、参数无效、服务异常。不要统一显示“空列表”。能读缓存时显示缓存内容与更新时间，失败的模块可独立重试。

缓存键至少包含 host、账号/可见性范围、资源 ID 和查询/ref。仓库重命名或转移不能仅靠旧 owner/name 永久识别。正式采用的 API 版本固定在配置里，升级时验证，避免散落在各页面。

## 10. 后续扩展要求

### 10.1 多主题

主题切换是已提出的后续方向。先保持内容、导航配置和业务状态独立于配色/排版。后续可以尝试更鲜明的黑白字排、紧凑工具风格等，但未确定主题数量、暗色方案、收费策略或任意主题编辑器。

### 10.2 AI 翻译

目标是降低 README、Issue、PR、发布说明的语言门槛。建议以用户主动触发为起点，保留原文切换，代码、路径、命令和 URL 不乱翻译；长文分段、缓存译文、允许重试，并标记 AI 生成。

模型供应商、自带 API key、服务端代理、成本与配额尚未决定。私有仓库内容是否发给外部服务，应在功能流程中让用户明确选择，不默认后台翻译上传。

### 10.3 镜像仓库配置

用户说的是“镜像仓库配置”，具体范围未明确。至少区分：

1. 关联一个仓库的镜像仓库地址，用于查看或获取内容。
2. 更换 Clone 源或源码归档源。
3. Release/文件下载代理或镜像。

这些不是同一种能力，也不等于把 GitHub API 全部重写到代理域名。后续应配置来源、适用资源、可用性与回退方式，展示当前数据/下载来源。GitHub 凭据不能自动发送到任意镜像主机；跨域下载重定向也需正确处理认证。

镜像信任、速度与文件一致性、是否支持私有仓库、默认服务及自定义规则都待确认。当前没有预设或认可某个第三方镜像提供商。

## 11. 原型使用和页面映射

### 11.3 推荐体验路径

8. 发布 → 模拟加入下载列表 → 资料库 → 下载；确认没有真实下载文件。
9. Actions → 失败运行 → 展开失败步骤 → 模拟重跑；确认只是演示。

### 11.4 存储、恢复与演示数据

源码沿用 `qiye-demo-` 的历史 localStorage 前缀，以保留已有体验记录；这只是原型内部兼容键，界面品牌已经统一为 RepoRove。保存项包括 preferences、stars、later、watching、unread、done、downloads、comments 与 Issue 草稿。

localStorage 按浏览器与页面来源隔离，文件版与 localhost 版可能不共享记录。恢复默认布局不清空收藏/评论。完整重置演示记录可在浏览器开发工具中仅移除 `qiye-demo-` 前缀的键；不要清空用户整个浏览器数据。限制本机存储的浏览器环境下，持久化行为需另行验证。

### 产品与视觉

- [ ] 使用 RepoRove 英文名，不擅自添加已定中文名或正式吉祥物。

- [ ] 勾选、隐藏、排序选项卡立即生效，重启后保留；边界数量处理清楚。

- [ ] 离线缓存、退出、账号切换不泄露其他账号的私有内容或凭据。

### 技术验证

- [ ] 关键测试验证用户行为与 API 边界，避免只检查实现细节或静态样式。
